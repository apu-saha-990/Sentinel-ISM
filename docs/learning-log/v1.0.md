## Learning checkpoints (from build plan, should be answerable without notes)
- [x] What `systemd` is, and how a unit differs from a plain running process
  > systemd manages services on Linux — checked with `systemctl` to get a real list of what's actually enabled/running, rather than just a process list, because a service can be set to auto-start even if it's not running right now.
- [x] What `auth.log` records and why it matters for ISM-0584
  > Ubuntu logs every login, failed login, and sudo action to `/var/log/auth.log`. The check confirms that file exists, has recent content, and isn't empty — verifying the logging mechanism itself works, not judging whether the security is good.
- [x] The difference between file permission checks (`stat`) and file content checks
  > A permission check (via `stat`) looks only at file metadata — owner, group, read/write bits — to answer "who's allowed to touch this file." A content check opens the file and looks at what's inside — line count, emptiness, recent activity — to answer "what does this file actually contain." ISM-1985/1815 (log protection) are permission checks; ISM-0584 (logging happens) is a content check. Never confuse the two — checking "protection" by reading file content would be a real bug.

## Notes (dated, as we go)

**2026-08-28 — The six ISM controls, plain-language understanding**

- **ISM-0383 (unneeded accounts/services disabled):** unused accounts and running services are extra attack surface for no benefit. Check lists every account and enabled service, compares against an allow-list, flags anything unexpected.
- **ISM-1508 (privileged access limited):** fewer accounts able to `sudo` means smaller blast radius if one gets compromised. Check looks at sudoers group membership, flags if it grows unexpectedly.
- **ISM-0584 (logon/failed logon/logoff logged):** confirms the system is actually recording login activity, via `/var/log/auth.log` existing, being written to, and non-empty.
- **ISM-1985 (logs protected from unauthorised access):** log files need to be unreadable by random users, or sensitive info (login patterns, attack attempts) leaks. Check is file permissions — not world-readable.
- **ISM-1815 (logs protected from unauthorised modification/deletion):** if a compromised low-privilege account can write to the log, an attacker can cover their tracks. Check is file permissions — not world-writable.
- **ISM-0988 (accurate/consistent time source):** wrong or drifting clocks make log timestamps useless for correlating events, and can break certificate validation. Check confirms a time-sync service (chrony/systemd-timesyncd) is actually running and synced, not just installed.

**Why these six specifically:** all of them are things directly observable on the machine right now (a file's permissions, a service's state, an account list) — none require judging intent or paperwork/process, which is why the original longer ISM list got trimmed down to these.

**2026-08-28 — Ubuntu Desktop vs Server, and why Server for sentinel-server**

- **Desktop:** full GUI (GNOME, file manager, browser, etc.) on top of the base OS — built for someone sitting in front of the machine.
- **Server:** same underlying OS/kernel, no GUI — boots to a text login, everything done via terminal (locally or SSH).
- **Why Server is right for sentinel-server:**
  1. Desktop runs many more background services by default (display manager, sound, notifications) — directly works against ISM-0383, since a clean baseline would require manually disabling a pile of GUI-related services first.
  2. sentinel-server is never touched directly — always SSH'd into from the host — so a GUI is pointless.
  3. Smaller footprint (less RAM/disk at idle), though resources aren't the constraint here.
  4. More realistic: real production Linux servers are almost always headless Server installs, not Desktop — closer to what the actual ASD role involves assessing.
- Mistake made along the way: first download from ubuntu.com's homepage grabbed Desktop by default — had to go specifically to the "Server" tab on the downloads page to get the right ISO.

**2026-08-30 — Building the real allow-list from actual VM state (ISM-0383)**

- Pulled real `/etc/passwd` and `systemctl list-units --type=service --all` from sentinel-server before writing any comparison logic — never guessed at what a "typical" minimized Ubuntu Server should have.
- Only two accounts (`root`, `sentinel`) have a real login shell; every other account uses `/usr/sbin/nologin`, `/bin/false`, or `/bin/sync` — these are system/service accounts, not something a person can log into. The check treats these structurally (by shell type), not by name, since a minimized install adds/removes them on its own.
- Found two running services (`multipathd`, `snapd`) with no clear justification for this VM's role (multipathd manages redundant storage paths — irrelevant with one virtio disk; snapd manages snap packages we're not using). Deliberately left both **off** the allow-list rather than guessing whether to keep them — this means the scanner correctly flags them as findings every run until an actual decision is made. Keeping them visible on purpose, not silencing them.
- **`active` vs `running` matters:** `systemctl --state=active` includes one-shot boot units that ran once and exited (e.g. `apparmor.service`, `kdump-tools.service`) — roughly 30 of them on this VM. Filtering on `--state=running` instead gives only the continuously-running daemons, which is what ISM-0383 actually means by "service enabled." Using `active` would have produced ~30 false-positive findings that have nothing to do with unneeded services.

**2026-08-30 — ISM-0584 (auth.log → journald) — third real collector check, a genuine scope correction**

**2026-08-30 — ISM-0988 (time sync) — fifth real collector check, sixth control checked**

**2026-08-31 — Why the VMs never asked for Wi-Fi, and how they get internet at all**

- Realized partway through today's work that I'd never actually understood how the VMs get internet access, despite using it for `apt` this whole time.
- The VM's network card (`enp1s0`) isn't real hardware — it's a *virtio* device, a virtual NIC that libvirt/QEMU presents to the guest OS. As far as Ubuntu inside the VM is concerned, it's just a normal wired ethernet card.
- That virtual NIC connects to a virtual bridge on ArtX (`virbr0` for the original network, `virbr1` for the new isolated one). The bridge runs a small DHCP server (`dnsmasq`) that hands out addresses automatically — this is why neither VM ever needed manual IP configuration to get online in the first place.
- When a VM sends traffic to the real internet, ArtX's kernel does NAT — rewriting the VM's packets to go out over ArtX's actual physical connection, then routing replies back to the right VM. The VM has no idea any of this is happening; it just sees "I have a NIC, I have an IP, there's a gateway."
- This is exactly why creating an "isolated" network for v1.1 didn't mean cutting off internet access — it's still NAT'd the same way, just on a separate bridge/subnet from the original one, so the two VMs are logically grouped together rather than mixed in with anything else that might use the default network later.

**2026-08-31 — Static IP via netplan, and a real console bug hit along the way**

- Plan: move each VM off DHCP onto a fixed address (sentinel-server → 192.168.100.10, sentinel-endpoint → 192.168.100.11) so the collector always knows where to find them, instead of relying on DHCP leases that (as documented) can drift.
