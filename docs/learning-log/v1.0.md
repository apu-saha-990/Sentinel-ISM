# Sentinel — Learning Log — v1.0

Filled in as work happens. Required before v1.0 is called complete.

## Learning checkpoints (from build plan, should be answerable without notes)
- [x] What `systemd` is, and how a unit differs from a plain running process
  > systemd manages services on Linux — checked with `systemctl` to get a real list of what's actually enabled/running, rather than just a process list, because a service can be set to auto-start even if it's not running right now.
- [x] What `auth.log` records and why it matters for ISM-0584
  > Ubuntu logs every login, failed login, and sudo action to `/var/log/auth.log`. The check confirms that file exists, has recent content, and isn't empty — verifying the logging mechanism itself works, not judging whether the security is good.
- [x] The difference between file permission checks (`stat`) and file content checks
  > A permission check (via `stat`) looks only at file metadata — owner, group, read/write bits — to answer "who's allowed to touch this file." A content check opens the file and looks at what's inside — line count, emptiness, recent activity — to answer "what does this file actually contain." ISM-1985/1815 (log protection) are permission checks; ISM-0584 (logging happens) is a content check. Never confuse the two — checking "protection" by reading file content would be a real bug.

## Notes (dated, as we go)

**2026-08-28 — The six ISM controls, plain-language understanding**

- **ISM-0383 (unneeded accounts/services disabled):** unused accounts and running services are extra attack surface for no benefit. Check lists every account and enabled service, compares against an allow-list, flags anything unexpected.
- **ISM-1508 (privileged access limited):** fewer accounts able to `sudo` means smaller blast radius if one gets compromised. Check looks at sudoers group membership, flags if it grows unexpectedly.
- **ISM-0584 (logon/failed logon/logoff logged):** confirms the system is actually recording login activity, via `/var/log/auth.log` existing, being written to, and non-empty.
- **ISM-1985 (logs protected from unauthorised access):** log files need to be unreadable by random users, or sensitive info (login patterns, attack attempts) leaks. Check is file permissions — not world-readable.
- **ISM-1815 (logs protected from unauthorised modification/deletion):** if a compromised low-privilege account can write to the log, an attacker can cover their tracks. Check is file permissions — not world-writable.
- **ISM-0988 (accurate/consistent time source):** wrong or drifting clocks make log timestamps useless for correlating events, and can break certificate validation. Check confirms a time-sync service (chrony/systemd-timesyncd) is actually running and synced, not just installed.

**Why these six specifically:** all of them are things directly observable on the machine right now (a file's permissions, a service's state, an account list) — none require judging intent or paperwork/process, which is why the original longer ISM list got trimmed down to these.

**2026-08-28 — Ubuntu Desktop vs Server, and why Server for sentinel-server**

- **Desktop:** full GUI (GNOME, file manager, browser, etc.) on top of the base OS — built for someone sitting in front of the machine.
- **Server:** same underlying OS/kernel, no GUI — boots to a text login, everything done via terminal (locally or SSH).
- **Why Server is right for sentinel-server:**
  1. Desktop runs many more background services by default (display manager, sound, notifications) — directly works against ISM-0383, since a clean baseline would require manually disabling a pile of GUI-related services first.
  2. sentinel-server is never touched directly — always SSH'd into from the host — so a GUI is pointless.
  3. Smaller footprint (less RAM/disk at idle), though resources aren't the constraint here.
  4. More realistic: real production Linux servers are almost always headless Server installs, not Desktop — closer to what the actual ASD role involves assessing.
- Mistake made along the way: first download from ubuntu.com's homepage grabbed Desktop by default — had to go specifically to the "Server" tab on the downloads page to get the right ISO.

**2026-08-30 — Building the real allow-list from actual VM state (ISM-0383)**

- Pulled real `/etc/passwd` and `systemctl list-units --type=service --all` from sentinel-server before writing any comparison logic — never guessed at what a "typical" minimized Ubuntu Server should have.
- Only two accounts (`root`, `sentinel`) have a real login shell; every other account uses `/usr/sbin/nologin`, `/bin/false`, or `/bin/sync` — these are system/service accounts, not something a person can log into. The check treats these structurally (by shell type), not by name, since a minimized install adds/removes them on its own.
- Found two running services (`multipathd`, `snapd`) with no clear justification for this VM's role (multipathd manages redundant storage paths — irrelevant with one virtio disk; snapd manages snap packages we're not using). Deliberately left both **off** the allow-list rather than guessing whether to keep them — this means the scanner correctly flags them as findings every run until an actual decision is made. Keeping them visible on purpose, not silencing them.
- **`active` vs `running` matters:** `systemctl --state=active` includes one-shot boot units that ran once and exited (e.g. `apparmor.service`, `kdump-tools.service`) — roughly 30 of them on this VM. Filtering on `--state=running` instead gives only the continuously-running daemons, which is what ISM-0383 actually means by "service enabled." Using `active` would have produced ~30 false-positive findings that have nothing to do with unneeded services.

**2026-08-30 — Non-interactive SSH access for the collector**

- The collector script runs on ArtX (the host) and reaches out to sentinel-server over SSH — it can't use interactive password prompts, since nothing is there to type a password when a script runs.
- Set up SSH key-based auth (`ssh-keygen` on ArtX, `ssh-copy-id` to sentinel-server) instead of storing the VM password for use by automation — more secure, and the standard approach for this kind of thing.
- Key path recorded in `.env` (`SENTINEL_SERVER_SSH_KEY`), not committed. Password auth still works for console/emergency access, but automation now uses the key exclusively.

**2026-08-30 — ISM-0383 collector check: first real result**

- `collector/checks/accounts_services.py` written and run for real against sentinel-server — first collector script to produce an actual (not simulated) result.
- Result: FAIL, 2 findings (`multipathd.service`, `snapd.service` running but not on the allow-list). This is the correct, expected outcome given the deliberate decision above — not a bug in the script.


**2026-08-30 — ISM-1508 (sudoers) — second real collector check**

- Pulled real sudo group membership from sentinel-server: `getent group sudo` → only `sentinel`.
- Checked `/etc/sudoers` and `/etc/sudoers.d/*` for custom rules beyond group membership — found nothing custom, just Ubuntu's shipped defaults (`root ALL=(ALL:ALL) ALL`, `%sudo ALL=(ALL:ALL) ALL`, and the default `/etc/sudoers.d/README` boilerplate). No unexpected privilege grants.
- Unlike ISM-0383, this allow-list had no ambiguous judgment call to make — one admin account, one expected sudoer, straightforward.
- Learned that `sudo` over SSH needs a real terminal to prompt for a password (`ssh -t`) — without it, sudo fails with "a terminal is required to authenticate" rather than prompting. The collector script itself doesn't need this, since it only reads group membership via `getent`, which needs no elevated privilege at all.
- Scope note: the check only looks at sudo *group membership*, not sudoers *file* content (e.g. NOPASSWD rules) — that's what the build plan specifies as checkable for this control. Deeper sudoers-file auditing would be a different, more detailed control, not part of ISM-1508 as scoped here.
- Result: PASS, 0 findings — `sentinel` is the only sudo group member and it's expected.


**2026-08-30 — ISM-0584 (auth.log → journald) — third real collector check, a genuine scope correction**

- Build plan assumed `/var/log/auth.log` would exist and be checkable directly. Real inspection of sentinel-server showed no such file, and `rsyslog` isn't even installed — this minimized Ubuntu Server install logs everything through `systemd-journald` only.
- This isn't a broken system — confirmed real, accurate login/logoff/sudo events are being recorded, just via a different mechanism than the build plan assumed. Verified with `journalctl -u ssh` first (saw real accepted-publickey logins with timestamps and source IPs), then broadened to grep on `pam_unix`, which catches SSH logins, sudo sessions, and console logins in one query — the closest real equivalent to what `auth.log` traditionally captured across all of those, not just SSH.
- Checked whether the collector (which runs unattended, can't type a sudo password) would even be able to read the journal without elevated privilege. Tested the exact non-interactive command the script would run — it worked with no sudo needed, because `sentinel` is already in the `adm` group by default on this Ubuntu install.
- Lesson: when a build plan's assumption turns out wrong for the real system in front of you, the right move is to investigate why, confirm the underlying security property is still genuinely being met, and adjust the check to match reality — not force a fake check against something that doesn't exist, and not skip the control either.
- Result: PASS — journald active, real pam_unix entries present and recent.


**2026-08-30 — ISM-1985 / ISM-1815 (log permissions) — fourth real collector check**

- Same file-not-what-was-expected situation as ISM-0584: the build plan's controls target log file permissions, but since this system has no `/var/log/auth.log`, the real target is the systemd journal files (`/var/log/journal/<machine-id>/*.journal`).
- Pulled real permission bits with `stat -c '%a %n'`: both journal files are mode `640`, owned by `root`, group `systemd-journal` — owner read/write, group read-only, others nothing at all. Not world-readable (ISM-1985 met) and not world-writable (ISM-1815 met), by systemd's own defaults, no manual hardening needed.
- Combined both controls into one check script since they examine the exact same files, just different bits of the same permission mode — checking the same file twice in two scripts would be redundant.
- This is a pure permission/metadata check (via `stat`), consistent with the v1.0 learning checkpoint distinguishing permission checks from content checks — no file content was read here, only `stat` output.
- Noted in `baseline.yml` that the journal path includes a random per-machine ID directory, so the check globs the path pattern rather than hardcoding the exact filename.
- Result: PASS — both journal files correctly restricted (mode 640), no world access of any kind.


**2026-08-30 — ISM-0988 (time sync) — fifth real collector check, sixth control checked**

- Straightforward one, no scope surprises unlike the previous two — `timedatectl` reports exactly what the control asks for directly.
- Two things checked, and they're genuinely different: whether an NTP mechanism is active at all (`NTP service: active`) versus whether the clock is actually, currently synchronized (`System clock synchronized: yes`). A service can be running without yet having achieved sync — e.g. right after boot, or during a network outage — so both need to be true independently, not just one implying the other.
- Confirmed `chrony` itself is the running NTP daemon behind this (already seen as active/running in the ISM-0383 services data), consistent across checks.
- Result: PASS — clock synchronized, NTP service active.
